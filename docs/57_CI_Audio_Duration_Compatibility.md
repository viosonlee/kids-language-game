# CI 音频时长误判修复

> Author / Agent: Codex  
> Date: 2026-10-03  
> Status: Local validation passed; remote rerun pending

本记录增量补充 docs/40、41、56，不改变音频响度、峰值和短鼓励音时长上限。

## 失败证据

用户提供的 Actions 日志显示 FFmpeg 6.1.1 安装成功，音频检查输出 128/129 后以状态 1 退出。用户随后提供 ci.json 的失败记录：audio/paopao/paopao_praise_effort.mp3，响度 -20.45 LUFS、峰值 -5.89 dBTP 均合格，但 format.duration 为 0.960 秒，大于 0.950 秒上限。

同一文件 SHA256 为 2b425625050e7e3e36e11d469472710ef34f5438f0e057d739adb7192769e649，本机 FFmpeg 8.1.2 报告 0.911375 秒。MP3 容器时长在版本间对编码延迟和补齐采样的计入不同，旧脚本把容器估计值直接用于实际播放时长门禁，造成跨版本结果不一致。

## 修改

- 检查脚本将音频解码到临时 PCM WAV，以采样帧数 / 采样率计算 duration_seconds；另保留 container_duration_seconds 供排查。临时文件退出后清理，不改写素材。
- 实测该文件为 21873 / 24000 = 0.911375 秒。响度、峰值、0.950 秒短语音及 0.550 秒提示音门禁不变，不裁剪、变速或重新编码现有发音。
- JSON 增加 failures 原因列表，控制台直接打印失败文件和超标指标；异常测量和不合格提示音也输出明确错误。检查失败仍返回状态 1，工作流继续保存现有报告附件。

## 验证与范围

- Python 29 项测试通过。新增跨版本容器时长 0.960 / 0.911375 的回归用例、真实超长/响度/峰值拒绝用例、CLI 失败日志及非零退出与报告用例。
- 本机全量解码测量 129/129 通过，success.wav 为 0.550 秒。素材文件无改动。
- 本次未在 Ubuntu FFmpeg 6 上执行完整检查；其旧容器测量来自用户提供的 CI 证据。推送会触发源码 CI，远端重跑结果尚待确认，不能以本机通过宣称整个 Actions 已绿。
- 该问题位于构建时质量检查，不是应用中英文语音识别缺陷；整体代码审查与实机验收仍继续。
